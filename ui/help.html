How DADS Works — End to End

DADS decides whether an intercepted radar emitter belongs to a known family, is an unknown emitter, or is noise. It classifies a window of k consecutive pulses of one emitter (a de-interleaved track): the input is a k × F matrix of per-pulse features, including Δ (change) features that expose the PRI pattern and the frequency agility. It decides per window and votes over a track's windows. The whole sequence-specific part — input, dataset, features, encoders, training, thresholds, testing, deployment — is described in S1–S11 (S11: adding a new family to a deployed model).

The steps F1–F6 below explain the parts every model shares: the two output heads, the training losses, the class prototypes, the prototype search and the embedding size, the decision rule, and the evaluation metrics. Each says what happens, gives the exact formula (taken from the code) and why. Symbols: F = number of selected per-pulse features, k = window length, K = number of classes, d = embedding size (Training setting, default 128 — see Embedding size & memory), ‖v‖ = vector length (L2 norm).

F1From fused features to two opinions — the output heads

Two different "fusions" — don't mix them up. DADS combines information twice, at two different points:

① Feature fusion (inside the Hybrid backbone)

The temporal CNN's 64 numbers and the temporal Transformer's 64 numbers are joined and mixed by a learned layer into one feature vector f (S4). This happens inside the network, before any decision exists, and only in the Hybrid backbone.

② Decision fusion (the "Fusion Verdict")

The two heads' opinions — classifier confidence and prototype distance — are combined by a fixed rule into the final verdict (F5). This happens after the network, for every backbone.

One feature vector, two heads. Whatever the encoder, it produces one vector f of d numbers per window (default d = 128). That same f feeds two separate heads, each answering a different question:

┌─► Classifier head ─► p (K probabilities) ─► class, confidence c "WHICH known family?" window ─► X̃ ─► encoder ─► f ──┤ └─► Metric head ─────► e (d numbers, ‖e‖ = 1) ─► nearest prototype ─► distance "LIKE ANY known family?" encoder = temporal Hybrid, CNN, Transformer or GRU — all produce the same kind of f (d numbers) Classifier head — one linear layer + softmax z = W_c · f + b_c W_c: K × d — one weight row per class, scored against f p_k = exp(z_k) / Σ_i exp(z_i) softmax: K probabilities, all ≥ 0, summing to exactly 1 class = argmax_k p_k confidence c = max_k p_k (between 1/K and 1) Metric head — two layers, then L2 normalization v = W_2 · ReLU(W_1 · f + b_1) + b_2 W_1, W_2: d × d e = v / ‖v‖ the EMBEDDING: a point on the d-dimensional unit sphere

Classifier head — a relative judgement

Compares the window against the known families only and says which fits best. Softmax forces the probabilities to sum to 1, so even a window unlike every family must be assigned to one of them — and if it lies far on one side of the learned class boundaries it gets a high confidence. High confidence means "clearly more like family A than the others", not "definitely family A".

Metric head — an absolute judgement

Places the window as a point in a space where training (triplet loss) packed each family into tight clusters. The distance to the nearest stored family prototype measures how typical the window is of anything known. A window from a never-seen family lands in empty space → large distance, whatever the classifier says.
Why both heads read the same f: during training both losses (cross-entropy from the classifier, triplet from the metric head) send gradients back into the same backbone, so f is shaped to serve both — separating families and forming compact clusters. One forward pass gives both outputs, and both opinions are about the same internal description of the pulse. The classifier has an output for every class id in the dataset; held-out classes are never a training target, so their outputs are only ever pushed down.

F2Training objective — what the network is optimized for

L = L_CE + L_triplet + λ_RPL · ( L_RPL + L_adv ) minimized with Adam, batches of 64, for the chosen epochs Cross-entropy (classifier head): push up the true class's probability L_CE = −log p_y Triplet loss (metric head): same-class embeddings closer than other-class ones by a margin α L_triplet = max( 0, d(e_a, e_p) − d(e_a, e_n) + α ) a = anchor window, p = random same-class window, n = random other-class window (picked within each batch) d = 1 − cos(·,·) for the cosine metric, d = ‖e_a − e_b‖ for euclidean Reciprocal Points Learning (RPL): one learned point o_k per class representing "not class k" d_k = ‖e − o_k‖² logits = γ · d_k (γ = 8) L_RPL = cross-entropy(γ·d, y) open-set score = −(d_top1 − d_top2) (small gap between the two farthest points = ambiguous = unknown) ARPL (optional): a generator G makes fake "confusing" embeddings ẽ for a class; the model learns to keep them ambiguous L_adv = mean( max(0, gap(ẽ) − 0.1)² ) while G separately minimizes cross-entropy(γ·d(ẽ), y)
Implementation note: in the current code the cross-entropy is applied to the softmax probabilities p (PyTorch's CrossEntropyLoss applies a softmax itself), i.e. the loss is −log softmax(p)_y rather than −log p_y. It still trains the classifier in the right direction but with weaker gradients. Kept as-is so existing runs stay comparable; changing it is a one-line fix that would alter future results.
Why these losses together: cross-entropy makes the classifier accurate on known families. The triplet loss shapes the embedding space — tight same-family clusters with margin α between families — which is what the prototype distance (open-set detection) relies on. RPL (λ_RPL, default 0.1) is a second, independently-scored open-set method trained on the same embedding, reported as its own AUROC so the two can be compared; the small weight keeps it from overpowering the main objective. ARPL hardens RPL's boundary with adversarial examples, at some cost in stability.

F3Class prototypes — summarizing each family in embedding space

for each known class c: E_c = embeddings of its validation windows if |E_c| ≥ 6: K-means with 3 clusters: minimize Σ_i min_{s=1..3} ‖e_i − μ_s‖² (10 restarts) else: one centre = mean(E_c) each centre μ_s → μ_s / ‖μ_s‖ (back onto the unit sphere)
Why up to 3 per class: one family appears in several operating modes, so its embeddings can form several separate clusters. A single average could land in the empty space between them, making genuine windows of that family look far from "their" centre. Sub-centres follow the real clusters. Validation (not training) windows are used so the prototypes reflect how the model behaves on data it wasn't fitted to.

F4Prototype search & distance

Every run stores its prototypes in prototypes.json: for each class up to 3 centre vectors of d numbers (the model's embedding size) plus metadata (class label, frequency band). For each window, its embedding e is the query, compared with every stored centre; the nearest one gives the label and the distance:

query q = e / ‖e‖ metric score s distance d (larger = more unusual) cosine s = q·c / (‖q‖ ‖c‖) d = 1 − s range 0 … 2 euclidean s = ‖q − c‖ d = s range 0 … 2 nearest prototype = the stored centre with the smallest d → label, frequency band, distance d
Why it works: training pulled same-family embeddings together (triplet loss), so "close in embedding space" ≈ "same family". Useful fact: because both q and every prototype have length 1, ‖q − c‖² = 2 − 2·cos(q, c). Cosine and euclidean therefore pick the same nearest prototype; they differ only in the distance scale (euclidean d = √(2·d_cosine)), so the distance threshold must be chosen to match the metric. Runs from before v1.2.0 may be labelled “dot”: that option was always computed as cosine (all vectors have length 1, so the dot product equals the cosine) and has been removed. The metric also sets the distance used inside the triplet loss during training.

F4bEmbedding size d — why 128, and how much memory it takes

What d is. One embedding = one vector of d numbers per sequence window. In DADS the backbone's feature vector f and the stored embedding e have the same size d, so d is the width of the whole "description" both heads read — not only the size of the stored prototypes. It is a Training-page setting (Embedding Size (d), in the Sequence Model card), recorded with every run (Run History column "Emb. d"); default 128.

the layers whose size depends on d (everything else is unchanged) backbone output layer (input width) × d (+ d) e.g. Temporal Hybrid fusion W_h: d × 128 classifier head W_c K × d (+ K) metric head W_1, W_2 d × d twice (+ 2d) → d-dependent weights ≈ (in + K) · d + 2d² memory per stored vector float32 4 · d bytes d = 16: 64 B d = 128: 512 B d = 256: 1 KB int8 quantized 1 · d bytes d = 16: 16 B d = 128: 128 B (not used by DADS) + metadata (label, band) prototypes in DADS: P ≤ 3 per class → 20 classes ≈ 50–60 points d = 128: 60 × 512 B ≈ 30 KB (float32) d = 16: ≈ 4 KB the same at library scale, 1,000,000 vectors (d = 128): 512 MB float32 · 128 MB int8

Measured: accuracy vs d. Temporal Hybrid sequence model: 12 families (2 held out), 24 tracks × 96 pulses, k = 32, 10 epochs, 2 datasets; same datasets and training settings, only d changed. Mean values:

Reading it: below 64 the accuracy drops (to 56% at d = 8) — not because small vectors can't be stored, but because f is also d wide: 8–32 numbers must carry 20 families × 4 operating modes, so families get squeezed together and the classifier confuses them. Unknown detection (AUROC) holds up longer (≥ 0.99 from d = 16), because "far from everything" is easier than "which one exactly". 128 is the smallest size that was at 100% on every dataset; 256 adds nothing (and was slightly less stable for the open-set score) while costing about 50% more weights. Caveats: one simulated population per seed, short training (15 / 10 epochs) — small d may close part of the gap with longer training; harder real data could need more room. Run your own comparison: train the same dataset with two sizes and compare the runs in Run History.
d and storage: changing the setting affects only the next training run — a trained model keeps its own d. Memory per stored vector grows linearly with d (4·d bytes in float32), which matters for very large prototype libraries rather than for DADS's few dozen prototypes.

F5Decision rule — fusing the two opinions into one verdict

For every window the server (and the downloaded package) runs the same sequence:

1. track pulses → per-pulse features → standardized k × F window X̃ (S3) 2. one forward pass → p (class probabilities) and e (embedding) (S4, F1) 3. confidence c = max_k p_k predicted class = argmax_k p_k 4. nearest stored prototype to e → its family label, band, distance d (F4) 5. compare c with τ_c and d with τ_d → verdict → ECM action if c ≥ τ_c and d ≤ τ_d : VERIFIED_KNOWN_TARGET → MONITOR_ONLY elif c ≥ τ_c and d > τ_d : UNKNOWN_THREAT_ANOMALY → AUTOMATED_JAMMER_ENGAGED else (c < τ_c, any d) : OOD_NOISE_REJECTED → ELINT_LOGGING τ_c = Min Classifier Confidence τ_d = distance threshold (both saved with each trained model — S6) the track's verdict is the most frequent window verdict (S7)

Worked example (illustrative numbers, cosine metric, τ_c = 0.60, τ_d = 0.30):

pulse top class (c) nearest prototype (d) verdict A known family 03 FAMILY_03 (0.94) FAMILY_03 (0.08) 0.94 ≥ 0.60, 0.08 ≤ 0.30 → VERIFIED_KNOWN_TARGET B never-seen family FAMILY_07 (0.91) FAMILY_07 (0.55) 0.91 ≥ 0.60, 0.55 > 0.30 → UNKNOWN_THREAT_ANOMALY C unstructured noise FAMILY_12 (0.38) FAMILY_02 (0.47) 0.38 < 0.60 → OOD_NOISE_REJECTED D known, between 2 families FAMILY_05 (0.52) FAMILY_05 (0.12) 0.52 < 0.60 → OOD_NOISE_REJECTED

Pulse B is why the rule exists: the classifier alone would have reported FAMILY_07 with 91% confidence. Only the distance shows that the pulse sits far from every prototype of family 07 — and of every other family.

Why this design:
• Confidence is checked first because a pulse the classifier itself can't place is too ambiguous to act on, whatever its distance — the conservative choice is to log it (ELINT) rather than jam it or trust it.
• Distance decides only once the classifier is confident — there it separates "confident and typical" (verified) from "confident but atypical" (unknown threat), the case softmax cannot detect on its own.
• The response follows severity: a confident-but-unknown emitter may be a new threat, so it gets the active response; verified emitters are monitored; ambiguous pulses are recorded for analysis.
Points to know:
• The rule does not check that the classifier's class and the nearest prototype's family are the same. Both are shown (Inference page, Live threat log); a disagreement is a useful warning sign worth inspecting, even when the verdict is VERIFIED.
• Region D (similar to a known family but unsure which) is grouped with noise. That is a conservative design choice — a pulse there is often a real known emitter whose mode lies between two families' clusters.
• Choosing thresholds: raising τ_d lets more pulses count as known (fewer false alarms, more new emitters missed); lowering it does the opposite. Raising τ_c sends more pulses to "rejected". A run's Evaluation tab (open-set ROC and verdict split) shows this trade-off for the actual model. τ_d is on the scale of the chosen distance metric (F4).
• The same rule runs in Inference, Testing, Live Simulation and the downloaded package, so they give identical verdicts for the same window.

F6Evaluation metrics

closed-set accuracy = (# known validation windows classified correctly) / (# known validation windows) precision_c = TP / (TP + FP) recall_c = TP / (TP + FN) F1_c = 2·P·R / (P + R) macro F1 = mean over classes open-set AUROC (score = prototype distance d; unknown should score higher) = P( d(random unknown window) > d(random known window) ) = ( R_U − n_U(n_U + 1)/2 ) / ( n_U · n_K ) R_U = sum of the unknowns' ranks among all scores ROC curve: for each threshold t, TPR = share of unknowns with d ≥ t, FPR = share of knowns with d ≥ t
Why AUROC: it measures how well the distance separates known from unknown independently of any threshold — 1.0 = perfect, 0.5 = guessing. The verdict split (Evaluation tab) then shows what your chosen τ_c and τ_d actually do. The RPL AUROC is computed the same way with RPL's own score, on the same split.

Upload your own tracks: Dataset page → Sequence Pipeline → Upload. instance and class (or true_class_id) are required plus at least one measurement column; files written with the earlier names (track_id, true_label, pri_us, carrier_freq_mhz, pulse_width_us, rise_time_ns, fall_time_ns, bandwidth_hz) are converted. Class ids are renumbered 0…N−1 (−1 stays unknown); the file becomes the Sequence Dataset that sequence models train on. A model trained on it reports the file's own class names (the class column), and a labelled test file is matched to the model's classes by those names — so its ids don't have to match.

Held-out families give an honest open-set test (the model has truly never seen them), and noise tracks model the junk a real receiver also intercepts. Bandwidth, fall time and the sequence patterns use separate random streams, so adding them never changes the values an existing seed produces.

Why: missed and spurious pulses are the two classic de-interleaver errors, so a model trained on clean tracks only would be over-optimistic. Each pattern's parameters come from a separate random stream ("sequence_patterns"), and PGRI from its own stream, so older seeds regenerate unchanged. Track length is exactly "pulses per track": generation continues until that many pulses were intercepted.

Your own measurements: any extra numeric column in an uploaded track file becomes a selectable sequence feature on the Training page, tagged from dataset — as its value per pulse and as its change from the previous pulse of the same track. It is scaled, trained, explained and packaged like the built-in features. Text columns, constant columns, mostly-blank columns and the reference columns of S2 are ignored. The track simulator can't produce such a column, so a model that uses one can't run on simulated tracks (Live Simulation → Tracks, example tracks, Testing's fresh tracks) — test and run it on track files that contain the column.
Why standardize: raw features differ by orders of magnitude (frequency ≈ 1010 Hz as the model sees it, pulse width ≈ 1 µs). Unscaled, the largest numbers would dominate the first layer and the gradients, and training would be slow and unstable. After scaling every feature has mean 0 and standard deviation 1, so each starts on an equal footing and the network learns their importance itself. μ and σ come from the training tracks only (no information leaks from validation or unknown tracks), are stored inside the model, and are reused unchanged by Testing, Inference, Live Simulation and the downloaded package.
Why keep both the value and its Δ: Δ alone loses the level (constant 400 µs and constant 800 µs both give ΔPRI = 0); the value alone hides the pattern from any single position. A temporal network could learn differences itself, but explicit Δ features make the pattern easy to learn and visible to permutation importance. Why the signed-log step for Δ: Δ values are heavy-tailed — a hopping family changes frequency by hundreds of MHz per pulse, a stepped family by tens of MHz, a fixed one by ~1 MHz of noise. A plain z-score divides all of them by one large σ (≈ 1.3 GHz), squashing the stepped family's steps to ≈ 0.05 — nearly invisible. After ln(1 + |Δ|/c) the three sit at clearly different levels (≈ 0.01 / 1 / 2–3 before the z-score), and the sign keeps the direction. Models trained before this step was added keep their original scaling.

Choosing the window length k, and why windows rather than whole tracks. A window can only reveal a pattern whose cycle fits inside it, so k should be at least about twice the longest PRI cycle you expect: a 4-level stagger repeats every 4 pulses (k = 32 shows it eight times), but a dwell-and-switch cycle can reach about 190 pulses, of which a 32-pulse window sees one level and perhaps one jump — the vote over a track's windows, and the frequency, PW and level themselves, carry those families. Windows are used instead of one input per whole track because (1) every track yields dozens of training examples instead of one, with every starting phase of the pattern; (2) a window has a fixed size whatever the track length (40 to thousands of pulses); (3) a decision is possible after a few pulses and improves as the track grows (Live Simulation) — a whole-track model must wait for the track to end. Joining all of a family's pulses into one long sequence is not an option: it glues different emitters together with artificial jumps and leaves one example per class. Longer patterns across windows can be captured by a learned aggregator over the windows' embeddings in place of the majority vote — not part of DADS yet.

S4Temporal encoders — running along the pulses

These encoders run across time — along the pulses of a window. All end in pooling over the pulses, so a model trained on k pulses also accepts shorter or longer windows.

Temporal 1D-CNN (seq_cnn) — features are channels, pulses are the axis h1 = ReLU(Conv1d_{F→64, width 3}(X)) each output sees 3 consecutive pulses h2 = ReLU(Conv1d_{64→128, width 3, dilation 2}(h1)) → 7 pulses h3 = ReLU(Conv1d_{128→128, width 3, dilation 4}(h2)) → 15 pulses f = ReLU(W · [mean_i h3 ; max_i h3] + b) W: d × 256 Temporal Transformer (seq_transformer) — one token per pulse, order from positional encoding t_i = W_in · x̃_i + b_in + PE(i) PE(i)_{2m} = sin(i / 10000^{2m/64}), PE(i)_{2m+1} = cos(i / 10000^{2m/64}) 2 layers of: T ← LN(T + MultiHeadAttention(T)), T ← LN(T + FFN(T)) (4 heads, d = 64, FFN 128) f = ReLU(W · mean_i(t_i) + b) Temporal Hybrid (seq_hybrid, default) — both encoders in parallel, fused by a learned layer f_cnn = Temporal CNN branch(X) (64 numbers) f_tf = Temporal Transformer branch(X) (64 numbers) f = ReLU(W_h · [f_cnn ; f_tf] + b_h) W_h: d × 128 — learned weighting of the two branches Bidirectional GRU (seq_gru) — recurrent baseline, hidden size 64, 2 layers z_i = σ(W_z x̃_i + U_z h_(i−1)), r_i = σ(W_r x̃_i + U_r h_(i−1)) h̃_i = tanh(W x̃_i + U (r_i ⊙ h_(i−1))), h_i = (1 − z_i) ⊙ h_(i−1) + z_i ⊙ h̃_i (both directions) f = ReLU(W · [mean_i h_i ; h_last(→) ; h_last(←)] + b) then the two heads (F1): p = softmax(W_c f + b_c), e = normalize(MetricHead(f))
Why these four: here neighbouring positions really are related (consecutive pulses), so convolution is natural — dilations let it see a whole stagger cycle or a dwell switch (15 pulses). The Transformer needs positional encoding because the order is the pattern. The Hybrid combines local patterns (CNN) with relations across the whole window (Transformer). The GRU is the classic recurrent baseline for comparison. Why pooling: mean/max over pulses makes the encoder length-agnostic, which is what allows decisions from the 2nd pulse in Live Tracks and the accuracy-vs-pulses curve. Export note: at inference the Transformer runs the same attention computation written with length-free reshapes (identical results), because PyTorch's own attention layer exports to ONNX with the training window length baked in — the downloaded model would otherwise only accept exactly k pulses.

S5Training split, windows, losses and prototypes

Stopping a long training run: press ■ Stop training on the Training page (it appears while a run is going). The run stops within one batch; nothing is saved for it and the model in use stays as it was. The status line always says what the run is doing (loading the dataset, building windows, training, calibrating, building the report); if a run fails, the reason is shown there with a hint — e.g. missing columns, NaN values or too little data. After a page refresh, a run that is still going is re-attached to its status line and Stop button.
split by TRACK and PER FAMILY (fixed split seed = dataset seed), as cross-validation: 1. test split: T % of each family's tracks (and of the unknown tracks) are set aside - never trained on (unless "Also train on the test split") 2. the remaining tracks of a family are cut into K buckets; fold f: validate on bucket f, train on the other K−1 buckets (T = 20 %, K = 4 → 20 : 20 : 20 : 20 : 20 - three buckets train, one validates, the fifth is the test split) 3. from each fold's training tracks 10 % per family are held back for calibration (S6) - too few → τ_d is calibrated on validation windows 4. every fold trains its own model (seed s + fold); the fold with the highest validation accuracy is kept. The run's accuracy / AUROC are the MEAN over the folds (the kept fold's own score is the best of several, so optimistic) and the kept model's result on the test split; "Cross-validation off" trains fold 1 only unknown tracks (held-out families + noise) → open-set pool (evaluation only); the test split's unknown tracks are left out of it windows: training stride k/2 (overlapping, more examples) validation / calibration / open-set stride k (no overlap) a track shorter than k gives no training window half of the training batches: every window cropped to a random 2 … k consecutive pulses scaling: μ, σ fitted on the training tracks' pulses only loss: L = CE + Triplet + λ_RPL · (L_RPL + L_adv) as F2 (Hyperparameters / RPL settings of the Training form) prototypes: ≤ 3 K-means centres per class from the training windows' embeddings (as F3); validation windows are only scored
Why a separate test split: validation tracks choose the kept fold and calibrate things, so they are no longer unbiased; the test split is touched only by the Testing page ("The model's held-out test split"), which marks it not independent when you trained on it. Why split by track: overlapping windows of one track are near-copies; splitting by window would put copies in both training and validation and overstate accuracy. Why per family: every family needs training tracks (its prototypes come from them) and validation tracks (to score it) — drawn from all families at once, a small dataset (e.g. 4 tracks per family) left some families with none. Why random crops: Live Simulation decides from the first few pulses of a track; trained on full windows only, the model classified 2-pulse windows right only 75–85% of the time — with crops, 94–100%. Why prototypes from training windows: windows that helped place a prototype sit unusually close to it, so scoring them against it makes the open-set AUROC look better than it is. Validation and open-set windows are therefore only scored, never used for prototypes. Why a separate calibration share: training windows sit unusually close to the prototypes too, so τ_d is calibrated on tracks used for nothing else — an honest estimate of how many fresh known tracks it accepts. Why the mean over folds: the kept fold is chosen because its validation score is the highest, so that score is optimistic; the mean over all folds (and the test split) is the fair estimate. Why a seed: weights, batch order, crops and triplets all follow the run's recorded seed, so a run can be repeated exactly. Training uses the Hyperparameters, Distance Metric and RPL settings of the Training form.

S6Sequence thresholds — the model's own τ_c and τ_d

τ_c: blank = the Training form's "Min Classifier Confidence"; or a value set on the Sequence Model card τ_d, Auto (default): d_j = distance of calibration window j to its nearest prototype (known tracks only) τ_d = quantile_q( d_1 … d_n ) q = "Known windows accepted", default 95% and per window length L < k (2, 3, 4, 6, 8, 12, 16, 24, …): the same quantile over the FIRST L pulses of each calibration track → τ_d(L) (never below τ_d); a window of n pulses uses τ_d of the largest L ≤ n kept to 6 significant digits (sequence distances are ≈ 0.001 — fixed decimals could round τ_d to 0) τ_d, Manual: the value you enter (one value for every length) Testing's τ_d override scales the per-length values by the same factor both are saved with the run; Run details → Thresholds shows the value, how it was chosen and on what ("24 held-out calibration tracks")
Why its own thresholds: a sequence model's embeddings are very tight (in the trace, known windows sit at d ≈ 0.001, while the Training form's default τ_d is 0.42) — a fixed default would accept most unknown tracks as known, so every model calibrates its own. Why per length: prototypes are built from full k-pulse windows; a 2-pulse window carries less evidence and always lands farther away (in the trace: 0.014 vs ≈ 0.001), so one τ_d made every new track "unknown" until ~8 pulses. With τ_d(L), known tracks are accepted at the same 95% rate from their 2nd pulse; unknown tracks are then harder to flag on very short evidence, which the accuracy-vs-pulses AUROC shows honestly. Why calibrate on known data only: τ_d is chosen without ever looking at unknown tracks, so AUROC and unknown-detection results stay honest. q is a direct trade-off: higher q → fewer known emitters flagged, more unknown ones missed. Testing can override τ_c / τ_d to explore the trade-off without retraining.

S7Track decision and metrics

window verdict = same rule (c ≥ τ_c, d ≤ τ_d) per window track windows: [1..k], [k+1..2k], … + one final window ending at the last pulse; a track shorter than k → one window of all its pulses track class = most frequent window class track verdict = most frequent window verdict (ties → the one seen first) — one rule shared by Testing, Inference, Live and the deployment package closed-set accuracy = share of known WINDOWS classified correctly open-set AUROC = AUROC of window distance d, known vs unknown windows (as F6) track accuracy = share of known TRACKS whose vote is the right class unknown tracks flagged = share of unknown tracks whose track verdict is NOT "verified known" accuracy vs pulses observed = one decision per track after its FIRST n pulses (n = 2, 4, 8, … 128), computed from those pulses only — exactly what Live Simulation decides at that moment; accuracy (known) and AUROC
Why vote: one window can be fooled (a mode switch, a burst of missed pulses); several windows of the same emitter agreeing is stronger evidence, exactly as an operator waits for a track to "settle". Accuracy vs pulses observed answers "how many pulses must be intercepted to identify the emitter". It starts at 2 pulses (the first decision possible) and uses nothing the receiver wouldn't have had at that moment. It appears in the run's details (Evaluation) and on the Testing page.

S11Adding a new family later: incremental training (Training page → Add New Families)

A deployed model meets a family it was never trained on; the open-set check flags it as unknown. Once its tracks are labelled, the model can be taught the family in four ways. Each makes a new model (a child of the base, “← #base” in Run History); the base model is never changed.

classes: the base model's labels L₀ (by name) + the new family's label(s); the classifier head grows to |L| rows, old rows keep their weights; a generated family that was held out keeps its RADAR_FAMILY id A frozen encoder + weight imprinting new data only, no training w_new = mean f(new windows) / ‖mean f‖ · mean‖w_old‖ b_new = mean b_old (f = backbone feature vector) prototypes: old ones unchanged + K-means of the new family's embeddings; τ_c, τ_d: the base model's B fine-tune with a replay buffer new tracks + R stored tracks per old family (from the base's training tracks) E epochs from the base weights, learning rate × s; loss = CE + triplet; prototypes and τ_d recomputed C fine-tune with distillation (LwF) new tracks only; the base model is the teacher loss = CE + triplet + T² · KL( softmax(z_teacher,old / T) ‖ softmax(z_old / T) ) + mean(1 − cos(e, e_teacher)), T = 2 prototypes of old families can only be kept from the base model (no old data to recompute them) D full retrain all old training tracks + new tracks, from scratch (the reference) scored on the same held-out tracks for every method and for the base model: old families the base model's validation tracks → forgetting = drop in old-family track accuracy new family a share (default 30%) of its tracks, never trained on by any method unknown the new dataset's unknown tracks (remaining held-out families + noise)

PDW (Pulse Descriptor Word) Fields

Carrier Frequency (fc)
The radio frequency the pulse was transmitted on, in MHz everywhere (track files: Frequency; Analytics, charts and the Dataset page too). Used for spectral band mapping and detecting frequency-agile emitters.
Pulse Width (PW)
How long a single pulse lasts, in microseconds (µs). Helps isolate the emitter's modulation mode.
PRI (Pulse Repetition Interval, ΔToA)
Time between consecutive pulses from the same emitter, in microseconds. Reveals the emitter's timing pattern — see PRI Modulation Patterns below.
PRF (Pulse Repetition Frequency)
The reciprocal of PRI (PRF = 1 / PRI), in Hz — how many pulses per second the emitter transmits. Shown on the Analytics page as an alternative view of the same timing information PRI carries.
Time of Arrival (ToA)
Precise timestamp the pulse was received, in nanoseconds. PRI is the delta between consecutive ToAs from the same emitter. Not a model input — an absolute timestamp says nothing about which emitter sent a pulse.
Fall Time
How quickly the pulse decays from full amplitude, in nanoseconds — like rise time, a transmitter hardware fingerprint. A selectable model input.
Bandwidth
Instantaneous signal bandwidth of the pulse, in Hz in track data (timeBW; the model sees it scaled to MHz) — wide for pulse-compressed or chirped waveforms (better range resolution), narrow for simple unmodulated pulses. A selectable model input.
PW × PRI
Derived: Pulse Width × PRI, in µs². A PW–PRI interaction term complementary to Duty Cycle (PW / PRI), computed on the fly from the Pulse Width and PRI already provided — no separate input needed. A selectable model input, also shown on the Analytics page.
Rise Time
How quickly the pulse reaches full amplitude, in nanoseconds — a subtle transmitter hardware fingerprint.
Duty Cycle
Fraction of time the emitter is actually transmitting: Pulse Width / PRI. Low duty cycle (search radars, long PRI) vs. high duty cycle (illumination/track radars, short PRI) is itself a strong Operating Mode signal. A selectable model input — computed on the fly from the Pulse Width and PRI already provided, since it's a genuine PW×PRI interaction a single linear classifier layer can't otherwise construct on its own. Also shown on the Analytics page as a percentage.

PRI Modulation Patterns

The six standard radar PRI modulation types from ESM / PRI-recognition literature, plus PGRI (pulse groups) — what PRI modulation recognition research actually discriminates between. Every simulated emitter class is assigned one of these.
Constant
PRI stays fixed at a single value, pulse after pulse — the simplest pattern.
Jittered
PRI varies randomly (small Gaussian noise) around a fixed mean, pulse to pulse — used to resist certain jamming/deception techniques.
Staggered
PRI cycles through a small number of fixed, discrete values in a fixed repeating order (e.g. A-B-C-A-B-C...) — used to resolve range/velocity ambiguities.
Sliding
PRI ramps continuously up and down between a minimum and maximum over time (a triangular sweep), rather than jumping between discrete values.
Wobulated
PRI oscillates smoothly (sinusoidally) between a minimum and maximum — similar intent to sliding, different waveform shape.
PGRI (Pulse Group Repetition Interval)
The emitter transmits groups of pulses: a few (here 2–8) at a short intra-group PRI, then a long gap; the groups repeat every PGRI. In a track the PRI sequence reads short, short, …, LONG, short, short, …, LONG — a strong periodic spike in ΔPRI. As independent pulses it is a two-level PRI distribution (mostly short, 1 in group-size long). Optional when generating a dataset ("Include PGRI", on by default); about 1 in 7 families are picked for it, and each group shape is fitted to the family's pulse width so pulses inside a group never overlap (PW ≤ 50% of the intra-group PRI in every operating mode); a family whose pulses are too wide for any group keeps its own pattern. Datasets and models from before it existed regenerate without it, exactly as before.
Dwell-and-Switch
PRI holds at one fixed value for a long block of pulses, then jumps to a different fixed value for the next block, and so on — distinct from staggered, which switches every pulse rather than dwelling.
Treated as independent pulses, only the steady-state distribution shape of each pattern is visible — staggered and dwell-and-switch are statistically indistinguishable without temporal order. The Sequence Dataset generates the real time order (stagger cycle, ramp, sine, dwell blocks, pulse groups — S2), which is what the sequence models learn from. Each row's pri_deviation_pct shows the pattern's contribution; Analytics → PRI Pattern Check verifies every family against its label.
Frequency Agility (sequence data)
How a family's carrier frequency changes from pulse to pulse in a track: fixed, hopping (a random channel every pulse), stepped (a repeating staircase of 3–5 steps) or burst (a new channel every 8–32 pulses). Recorded in the freq_agility column; visible to the sequence model through Δfrequency.

Operating Modes

Real multifunction radars don't emit with fixed parameters — they switch between modes that change frequency, pulse width, and PRI together, generally escalating as a target is acquired and tracked (the "war mode" search → lock-on progression), though an emitter can also lose lock and de-escalate.
Search
Wide-area scanning for any target. Longest PRI, widest pulse width, slightly lower frequency, lowest duty cycle — optimized for range/coverage over precision.
Acquisition
A candidate target has been detected; the radar narrows its focus to confirm and localize it. Baseline (1.0×) frequency/PRI/pulse-width multipliers — the reference mode the other three are defined relative to.
Track
Continuously following a confirmed target. Shorter PRI, narrower pulse width, slightly higher frequency, higher duty cycle than acquisition — trades coverage for update-rate precision.
Illumination
Highest-fidelity lock-on, typically immediately preceding weapon guidance or engagement. Shortest PRI, narrowest pulse width, highest frequency and duty cycle of the four modes — the most operationally significant mode to detect promptly.
Mode Diversity vs. Mode Persistence
In the Sequence Dataset and in Live Simulation each emitter has persistent state: it dwells in one mode for a block of consecutive pulses (15–60 pulses) before a biased random transition (50% escalate, 30% de-escalate, 20% jump) decides the next mode — so the escalation is something you can actually watch unfold over a track, not just a diversity statistic.

Dataset Generation Pipelines

The Dataset page holds the datasets (tracks) the sequence models train on and are tested on.
Sequence Dataset (Sequence Pipeline)
Tracks: ordered pulses of one emitter each, as a de-interleaver delivers them — used to train and test the sequence models. Settings: name, classes, held-out classes, tracks per class, pulses per track, missed / spurious pulse rates, noise tracks %, Include PGRI. Every dataset is kept under its name and listed on the Dataset page (view, make default, download, delete); Training, Testing and Analytics choose from that list, and each trained model remembers its dataset. The PRI types are handed out round-robin to the families (known ones first), so with six or more families every type appears. Bandwidth is in Hz. Generated (S2) or uploaded (S1).
Duty Cycle Range (population setting)
Dataset page → Advanced: Population Ranges. Each family's pulse width is set from its duty cycle: PW = duty × PRI, the duty cycle drawn log-uniformly from this range (default 0.1–10%, typical of pulsed radars; search radars sit at the low end, track/pulse-Doppler radars at the high end). This guarantees a pulse is never longer than the interval between pulses — drawing PW and PRI independently used to produce impossible families (duty cycle above 100%). Pulse Width Min/Max still limit the result; if both can't hold for a family's PRI, the duty-cycle range wins. Operating modes and PRI patterns then raise a family's duty cycle by at most about 2× (illumination shortens PRI more than PW), so pulses stay below ~20% duty, and PGRI pulses inside a group below ~50%. Recorded with each dataset and model, so Testing's auto-generated tracks use the same range.
Datasets — names, default, deleting
Every dataset (generated; uploaded for training; uploaded on the Testing page) is kept under its name and listed in All Datasets on the Dataset page: view it, make it the default (what the Training page offers first), download it as CSV or delete it. Training and Testing each have a dataset dropdown, Analytics lists every dataset plus the dataset behind each kept model, and each trained model records its dataset name (Run History, run details, model selectors, Test History), so the dataset in force is always visible. Deleting a dataset does not touch models trained on it; Analytics rebuilds a generated model's dataset from its seed (exact), but cannot for a deleted upload. Models from before names existed show “unnamed (seed …)”. A name always means the same data. Each dataset keeps a SHA-256 fingerprint of its file: the first 8 characters are shown next to the name in All Datasets, and hovering shows all of it. Every training and test run records the fingerprint of the data it used. A deleted dataset's name is retired and never given to another dataset, so a model can't silently point at different data. If a model's dataset file has been changed outside DADS, Testing on its test split, example tracks, Analytics and incremental training refuse it with a message instead of using different data.
PRI types handed out round-robin
New datasets give the families the six PRI types in turn (known families first, then held-out ones; PGRI families keep theirs) instead of drawing each at random, so with six or more families every type — staggered included — is present. Older datasets and models used random draws and regenerate exactly as before (recorded as balanced_patterns).
Modlntype, Modlnval, snr
New columns of the pulse data: Modlntype is the intra-pulse modulation of the family (None, LFM, NLFM, Barker, BPSK, Frank), Modlnval its parameter (chirp rate in MHz/µs for LFM/NLFM, code length for the phase codes, 0 for none) and snr the signal-to-noise ratio in dB of the capture (a condition of the capture, not of the emitter - a model that leans on it is suspicious). As model inputs they are the features Modulation Type (text, fed as the position in the modulation list), Modulation Value and SNR.
Extra features (your own columns)
Dataset page → Generate → Extra features: add a column to every generated pulse - numeric (each family gets its own value in [min, max], pulses scatter by a noise %) or categorical (each family gets one of your values). It is stored in the dataset, offered on the Training page as a feature (col: value, dcol: change per pulse, cat: category - fed as a stable number per category), and reproduced for the Testing page's fresh tracks, Inference examples and Live Simulation, so the same feature is used in training and testing.
Grow a small dataset into a large one
Dataset page → "Grow a Small Dataset into a Large One". Every class is topped up to the track count you give: a new track starts from one of the class's own tracks at a random point of its pulse pattern and, when the class has several tracks, differs by the spread those tracks show (each measurement scaled - SNR shifted - by a random amount within ±2 standard deviations of the between-track variation). No noise is added; the source dataset is unchanged. A class with a single track varies only in where its pattern starts, so one example per class gives a large but not very diverse dataset.
Test split, folds, cross-validation
Training page → Data Split & Cross-validation: Test split % of every class's tracks is held out; the rest is cut into Folds buckets and each fold validates on one and trains on the others (see S5). The run history shows the kept model's accuracy with the fold mean ± std; the run details list every fold. Also train on the test split moves the test tracks into every fold's training pool (for a final model) - the Testing page then flags that split as not independent. Training takes about as many times longer as there are folds.
Units: frequency in MHz, bandwidth in Hz
Track files carry Frequency (MHz) and timeBW (Hz); the Dataset page's frequency range is entered in MHz and its bandwidth range in Hz. Files with the older carrier_freq_hz column are converted on upload and on load, and the model still receives frequency in Hz, so earlier models behave identically. Likewise, files with the older bandwidth_mhz column are converted on upload and on load; the model itself still receives the value scaled to MHz, so models trained before the change behave identically.
Include PGRI
On by default for new datasets. About 1 in 7 families use the PGRI pattern (a family whose pulses are too wide for a pulse group would keep its own pattern — rare with the default duty-cycle range). Recorded with the dataset and every model trained on it, so auto-generated test data reproduces the same population; datasets and models from before it existed regenerate exactly as before.

Model & Hyperparameters

Dataset Feature (new feature from real data)
Any extra numeric column in an uploaded track file (e.g. aoa_deg) automatically appears under the Sequence Model card's Per-pulse Input Features, tagged from dataset — as its value per pulse and as its change from the previous pulse (Δ). Train, test and run Inference with it like any built-in feature. The track simulator can't produce it, so Live Simulation, example tracks and Testing's fresh tracks are unavailable for a model that uses it — use track files that include the column (S3).
Neural Model Backbone
The shared feature extractor before the two output heads. The sequence models have four temporal backbones that run along the pulses of a window: Temporal Hybrid (default; CNN and Transformer in parallel, fused by a learned layer), Temporal 1D-CNN, Temporal Transformer and Bidirectional GRU. Formulas and the reasoning: S4.
Sequence Model card (Training page)
Sequence Backbone (S4). Window k: pulses per window (default 32, 2–512). Epochs. Sequence features: any of PRI, ΔPRI, frequency, Δfrequency, PW, ΔPW, bandwidth, rise, fall, duty cycle, PW × PRI, plus dataset columns of an uploaded track file (S3). Min classifier confidence τ_c (blank = the form's value). Distance threshold τ_d: Auto (calibrated so "Known windows accepted" % of held-out known windows pass, default 95%) or Manual (S6). Uses the form's Hyperparameters, Distance Metric and RPL settings.
Training Dataset (Training page)
Which stored dataset the next sequence model learns from (default: the dataset marked “default” on the Dataset page). The feature list shows which columns that dataset offers. The run records the dataset's name.
Embedding Size (d)
How many numbers describe each sequence window: the size of the encoder's feature vector f and of the stored embedding (one vector per window). Options 8–256, default 128, set in the Sequence Model card and recorded per run. Measured on simulated data: accuracy falls below d = 64 (56% at d = 8), 128 was the smallest size at 100%, 256 gains nothing. Memory: weights change only slightly (0.68–1.34 MB for the Temporal Hybrid), a stored vector is 4·d bytes. Details: Embedding size & memory.
Embedding Distance Metric (Distance Metric)
How far apart two embedding vectors are, used in exactly two places — the triplet loss while training and the distance to the nearest class prototype checked against τ_d afterwards. It is plain arithmetic on the model's output vectors: Cosine (angle between vectors) or Euclidean (straight-line distance). Embeddings and prototypes all have length 1, so the two pick the same nearest prototype and differ only in distance scale — set the OOD Distance Threshold for the metric you use. See F4.
Learning Rate
Step size for the Adam optimizer during training. Too high can destabilize training; too low makes it slow to converge.
Triplet Margin (α)
Minimum gap the triplet loss enforces between "same-class" and "different-class" embedding distances. Larger margins push classes further apart in embedding space, but can make the loss harder to satisfy.
Min Classifier Confidence
Softmax confidence threshold. Below this, a window is treated as low-confidence regardless of the prototype distance, and rejected as OOD (Out-of-Distribution) noise.
OOD Distance Threshold
Prototype distance threshold. Above this, the nearest known prototype is considered too far away to trust — the window is flagged as anomalous rather than a confident match. Sequence models calibrate their own (S6).
RPL Loss Weight
How strongly the auxiliary Reciprocal Points Learning (RPL) objective shapes the shared embedding space during training, relative to the primary classifier + triplet losses (default 0.1, deliberately modest so RPL can't destabilize the proven primary training).
Enable Adversarial Training (ARPL)
Upgrades RPL to the full ARPL (Adversarial Reciprocal Points Learning) mechanism: a generator network adversarially synthesizes "confusing" embeddings targeting each known class, and the classifier is trained (in a min-max game) to keep rejecting them as open-space even as the generator tries to make them pass as genuine. Tightens the decision boundary beyond RPL's passive open-space margin loss, at the cost of a less stable, sometimes slower-converging run. Off by default — toggle it and retrain to get a genuine RPL-vs-ARPL comparison across two separate runs (both show up in Run History, each labeled with which mode produced its AUROC number).
Dataset Seed
Controls both which radar-family archetypes (frequency/pulse-width/PRI/rise-time) get generated and which classes are randomly held out — a fresh seed is drawn every time a dataset is generated for genuine diversity. Testing's auto-generate mode reuses the exact seed, ranges, noise level and PGRI setting of the model being tested, so it evaluates the same population that model was trained on — new tracks, same families.

Run Details — Formulas
The exact layer-by-layer computation of that trained model, generated from its real architecture: the window shape and input scaling (x̃ = (x − μ)/σ, with the fitted μ, σ and the Δ log scales), the temporal encoder, the classifier softmax, the normalized embedding, the prototype distance, and the decision rule with its thresholds. Weights by Layer / First-Layer Weights
Statistics (shape, count, mean, std, min, max, L2 norm) of every learned weight matrix, plus the first layer's weights — the only weights that touch the inputs directly.
Feature Influence
Permutation importance: validation accuracy lost when one feature's values are shuffled across windows, breaking its link to the class — how much the trained model actually relies on that feature. Unlike the Analytics feature ranking (which measures the data), these measure the trained model.
Hybrid Branch Contribution
Temporal Hybrid models only: the 1D-CNN's or the Transformer's 64 output numbers are set to 0 (branch switched off) or to their average over the validation windows (window-specific information removed), and accuracy and AUROC are re-measured with everything else unchanged. Also shows each branch's share of the signal entering the fusion layer, and how many of its 64 outputs are typically active. Formulas: S10.
Confusion Matrix / Per-Class F1 / ROC
Recorded for every run on its validation rows: which classes are confused with which, precision/recall/F1 per class (and macro F1), the open-set ROC curve behind the AUROC number, and how the fusion rule's verdicts split for known vs. unknown rows at the configured thresholds.

Adding New Families (Incremental Training)

Training page → Add New Families. Method formulas: S11.
Base model / child model
The base is the trained model that meets a new family; each method makes a new child model from it (“← #base (method)” in Run History). The base is never modified, so you can always go back.
Catastrophic forgetting
Training a network on the new family alone pulls all weights towards it; accuracy on the old families collapses because nothing reminds the network of them. Every method here is a different way of avoiding it. Measured as the drop in old-family track accuracy against the base model.
Replay buffer (method B)
A few stored tracks of every old family (default 10 per family), mixed with the new tracks while fine-tuning, so the old families keep being rehearsed. It also lets the old prototypes and τ_d be recomputed with the updated encoder. The buffer is a small subset of the base model's own training tracks.
Weight imprinting (method A)
Adds the new family without training: its classifier row is set to the average encoder feature vector of its tracks (scaled like the existing rows) and its prototypes are added. Fast and cannot disturb old weights or prototypes — but the new row competes with the old ones for every window, and the encoder was never trained to separate the new family, so old families are usually hurt.
Distillation / LwF (method C)
Learning without Forgetting: no old data; the base model acts as a teacher and the new model is trained to keep its softened class probabilities over the old families (KL divergence, temperature T = 2) and its embeddings (1 − cosine). Old families' prototypes can only be kept from the base model, so they go stale as the encoder shifts — which mostly shows up in the distance check (AUROC, “verified known”).
Full retrain (method D)
All old training tracks plus the new tracks, from scratch. The reference: most reliable, most expensive, needs the old data to be kept.
Comparison table
Base model and each method scored on the same held-out tracks: old families (the base model's validation tracks), new family (30% of its tracks kept aside, never trained on), unknown tracks (remaining held-out families and noise). Columns: track accuracy on old (with change versus base) and new; windows verified known (passing τ_c and τ_d) for old and new; unknown tracks flagged; open-set AUROC; time; data used. Comparisons are saved and listed under Earlier comparisons.
Simulate new-family data
For studies without real intercepts: fresh tracks of families the base model was trained without (its held-out families, same simulated population), labelled by their names, plus the remaining held-out families and noise as unknown tracks. Needs a base model trained on a generated dataset. With real data, upload the new family's labelled tracks on the Dataset page; families are matched by true_label name.
When to use which
Old data can be kept → B (usually near D at a fraction of the cost); no old data kept → C, expect weaker prototypes; almost no new data or an instant stopgap → A, then B once more tracks arrive; many families added over time, or results degrading → D. Always check the comparison — old families no worse, the new family above target, unknown rejection kept — before putting a child model in use.

Training & Validation Metrics

Closed-Set Accuracy
Fraction of windows from known (trained-on) classes that the classifier head predicted correctly.
Open-Set AUROC (Threshold)
AUROC (Area Under the ROC — Receiver Operating Characteristic — Curve) for using embedding-distance-to-nearest-centroid as an anomaly score, evaluated on classes held entirely out of training. 1.0 = perfect separation of known vs. unknown; 0.5 = no better than random guessing. This is the method the Fusion Verdict logic actually uses (compared against the OOD Distance Threshold). Each class contributes up to 3 centroids (via K-means clustering over that class's embeddings), not one mean — a class whose true population spans multiple Operating Modes can have sub-clusters far enough apart that a single mean would land in the empty space between them, making genuine same-class samples look falsely anomalous. "Distance to nearest known" now means nearest of all sub-centroids across all classes, not nearest single mean per class.
Open-Set AUROC (Reciprocal Points)
A second, independently-trained open-set method — RPL (Reciprocal Points Learning) — scored the same way (AUROC) on the exact same train/val/holdout split, so the two numbers are directly comparable. Instead of representing each class by what it IS (a centroid), RPL learns a "reciprocal point" per class representing what it ISN'T, plus a learned per-class radius bounding how far a genuine sample of that class may drift from its own reciprocal point. Farther-than-radius = flagged unknown. This gives each class a finite, bounded acceptance region instead of softmax's open-ended one — the mechanism behind the ARPL (Adversarial Reciprocal Points Learning) line of current open-set radar literature. Trained jointly with the main model as an auxiliary objective (a small fixed loss weight, so it doesn't destabilize the primary training) — it does not replace the threshold method, both are reported from the same run.
Holdout Classes
Radar classes deliberately excluded from training so open-set detection can be measured honestly — the model has genuinely never seen them, unlike ordinary noise.
Noise Percentage (Unstructured OOD)
Fraction of unstructured, agile OOD (Out-of-Distribution) pulses (no coherent class structure at all — not just "a radar type we didn't train on") mixed into the open-set evaluation pool alongside the holdout classes (as whole noise tracks in the Sequence Dataset). Real intercepted environments contain both novel-but-structured emitter types and outright junk/noise signals, so a thorough open-set evaluation should include both. Set on the Dataset page as Noise Tracks (%); Testing's auto-generate mode reuses the exact percentage the model was trained against, same as it reuses the dataset seed and ranges.
Track Accuracy / Unknown Tracks Flagged (sequence)
Sequence models are also scored per track: track accuracy = share of known tracks whose majority vote over windows is the right class; unknown tracks flagged = share of unknown tracks (held-out families + noise) with more than half their windows not verified as known. Closed-set accuracy and AUROC of a sequence run are per window. Formulas: S7.
Accuracy vs Pulses Observed (sequence)
The same trained model scored on the first 2, 4, 8, … 128 pulses of each track: how many pulses of an emitter must be intercepted before it is identified (no decision is possible from 1 pulse — there is no PRI yet).
Training Loss
Cross-entropy (classifier head) + triplet loss (metric head) + RPL Loss Weight × (RPL loss + ARPL rejection loss, if enabled) on each training batch, averaged per epoch (formulas: F2). Trending down means the model is fitting the training data; a plateau means further epochs are giving diminishing returns.

Fusion Verdicts & ECM (Electronic Countermeasures) Actions

Every window (and, by vote, every track) gets one verdict, produced by combining the classifier head's confidence with the prototype-distance check — neither signal is trusted alone.
VERIFIED_KNOWN_TARGET
